# Repository guidance

## Source of truth

- Read `property-simulation-sandbox-spec.md` as the document index, then consult the relevant topic document under `docs/` before changing architecture or domain behavior.
- `docs/implementation-roadmap.md` is the current milestone source of truth; `docs/domain-model.md` owns simulation and accounting semantics; `docs/architecture.md` owns dependency boundaries; `docs/engineering-practices.md` owns code-quality gates. Where retained legacy section text conflicts with the current roadmap, follow the roadmap and the topic-specific current baseline.
- Record consequential domain and architecture decisions as short ADRs under `docs/adr/` when that directory is created. Include the decision, alternatives considered, consequences, and test vectors where applicable.

## Domain design

- Keep the simulation core independent of CLI, GPUI, SQLite, and file export. Interfaces call the core; domain rules do not live in UI or command handlers.
- Treat time as inclusive `YearMonth` intervals and support runs starting from any valid, sufficiently complete state. Do not impose a fixed simulation duration.
- Preserve all known user-provided and previously generated variables required for continuation. Distinguish initial facts from events generated during the simulated interval; never invent past transactions to explain an opening state.
- The simulation is externally bounded and does not pause for domain decisions or model household solvency, bankruptcy, loan delinquency/default, or foreclosure in the initial scope. Negative property cash flow and economically unusual but computable outcomes are generated results, not failure conditions. Reject only structurally invalid or uncomputable input, not outcomes judged unrealistic. Provide a monthly pre-generation input boundary. Each month-end snapshot can seed a new branch; retain the parent branch and record changed inputs/effective month. A new branch uses a new random trial stream, so even unchanged parameters may yield different outcomes. Keep rules and inputs explicit and consistent within each branch; the application version identifies the software build.
- Scope runtime state by scenario: one in-memory `SimulationArchive` owns one scenario's settings and run history, and each run advances month by month. The core does not manage a multi-scenario collection or its scheduler. CLI/GUI may manage independent scenario archives and choose sequential or concurrent execution at the application layer; this does not impose a single-thread limit on the process.
- Keep events (what happened), decisions (chosen response), effects (state changes), and ledger transactions (economic postings) distinct and traceable.
- Slices propose changes. A shared coordinator validates conflicts and commits world-state effects and balanced journal transactions atomically. Slices must not mutate shared state or ledger directly.
- Use decimal fixed-point money, explicit currency and rounding policies. The initial single-currency rule rounds posted positive amounts to the currency minor unit using half-up; do not use binary floating point for posted amounts.
- Use double-entry accounting. Every posted journal transaction must balance. Derive account balances and financial statement/cash-flow views from opening balances and posted entries; do not maintain competing hand-written totals.
- The initial accounting profile represents a household/personal property owner. Keep accounts focused on property assets, financing, rental income, and operating expenses; do not add corporate or tax-accounting behavior without an explicit design decision.
- The initial mortgage convention is annual interest settled monthly. Before implementing calculations, consult the relevant ADR for the exact rate conversion, accrual/payment order, precision, and rounding rule; do not silently assume these details.
- Randomness is part of the core model. Distinguish probability distributions (what values are modeled) from random-stream allocation (how trials and slices receive random inputs). Keep trial ID, optional diagnostic seed, and stream derivation explicit. The application version is the only software version identifier; do not add independent model or random-stream version fields. A fresh simulation branch may produce different results; exact repeated output is not a product invariant. Test rule/input traceability, branch isolation, independent stream allocation, and commit safety. Fixed seeds remain useful for tests and diagnostics.
- Organize random models by domain category (environment, physical property/component state, policy/macro conditions, occupancy/operations). Assume independent streams across categories in the initial model and record that assumption; do not add hidden cross-category correlation. Any later correlation model must be explicit and change with the application as a whole.

## Implementation and verification

- Prefer small, typed domain interfaces and explicit validation over a general DSL, plugin framework, or speculative abstraction.
- Make extensibility a primary design criterion: adding a domain input or Slice should normally extend its types, validation, and strategy implementation without rewriting the runner, ledger, or presentation. Do not promise backwards compatibility across application upgrades; the application version identifies the build as a whole.
- Keep responsibilities separated even before final crate/module names are chosen: domain rules, application/service orchestration, configuration parsing, data access/infrastructure, unit-of-work/commit coordination, and CLI/GUI presentation have distinct boundaries. Domain must not depend on IO or presentation; presentation must not contain business rules; infrastructure implements ports instead of being called directly from domain code.
- Treat separation of concerns and dependency direction as acceptance criteria for every milestone and code review. Explain the responsibility and dependency direction of new modules. Avoid both mixed-layer modules and unnecessary micro-modules or pattern boilerplate.
- Use a single documented Rust format/lint/check workflow established with the project skeleton (at minimum rustfmt check, Clippy, compilation, and the relevant tests). Keep warnings visible; justify narrow lint exceptions. Do not claim checks that were not run.
- Test domain rules without IO; test application orchestration through in-memory/fake ports; add integration tests at actual serialization/storage/composition boundaries as those layers arrive. Keep tests deterministic with fixed inputs and seeds.
- M5 covers in-memory core data only. SQLite persistence and file export belong to the later application layer; do not define a general external schema, schema versioning, migration, or cross-upgrade compatibility promise. CLI/GUI parse and constrain user input formats; core validation enforces domain invariants and cross-field constraints required for correct computation.
- Treat the unit of work as the atomic commit boundary for related state effects, journal transactions, events, and snapshots. Verify failure does not partially commit and retries cannot duplicate a posting.
- Add unit tests for domain mathematics and invariants, plus continuity and composition tests for behavior across periods and slices. Simulation duration is test data, not a product constraint; use 24/240-month fixtures only when they add useful coverage.
- When changing a domain rule, update its ADR/specification and relevant test vectors together. Persistence is deferred; record the application version at the application/run or dataset boundary when that layer is introduced, without separate schema, model, or random-stream versioning.
- Do not introduce CLI or GPUI dependencies into core crates.
- Before finishing a change, report what changed and which checks were run. Do not claim checks that were not run.
