# 领域模型与月度模拟语义

> 本文保留原规范章节编号，便于和既有讨论对应。首版实施基线以本文及 [实施路线](implementation-roadmap.md) 为准。

## 5. 时间模型与月度执行语义

### 5.1 月份

`YearMonth` 采用 YYYY-MM；若运行设置 `end_month`，则 `[start_month, end_month]` 为包含边界。也可不设置结束月份，由月末终止条件或外部逐月控制决定是否继续。月份而非天是模型的基本精度。无日级真实付款日、罚息或天气逐日轨迹的保证。

### 5.2 月度状态

每个 `MonthlyPeriod` 具有：month、opening snapshot reference、proposed/committed events、decisions、state effects、ledger transactions、closing snapshot reference、monthly totals、status。

### 5.3 规范化执行阶段

1. **Input**：月度计算前接收本月外部输入/假设更新，校验并冻结生效于本月的输入快照。调用方可以每月提交更新，也可以在快速运行中持续提交不变的输入；两者使用同一月度执行流程。
2. **Open**：读取上月 closing state（首月读取 initial state）。
3. **Context**：建立本月共享环境输入和只读视图。
4. **Accrue/Evolve**：计算月度过程（例如老化、计息），生成候选 Effects。
5. **Propose**：各 Slice 根据状态、计划和随机输入提出事件、经济流水。
6. **Resolve**：按依赖和优先级处理跨 Slice 关系、验证前置条件、解决冲突。
7. **Commit**：原子应用状态 Effects 和 Ledger Transactions；确保只提交一次。
8. **Close**：计算月度汇总、生成月末快照、推进到下月。

**注意：** 这是语义阶段，不要求所有 Slice 都在同一时刻读取旧状态后无条件相加。存在依赖时必须按依赖拓扑顺序/显式阶段读取已提交的中间结果，或重新计算受影响 Proposal。

### 5.4 同月因果顺序

示例：本月租客搬离 → 本月租金是否收取，由租赁规则决定；不得简单让两个 Slice 各自输出矛盾结果。推荐每个 Slice 声明读/写资源、前置条件和依赖。执行器先确定相关事实，再产生依赖它的后续经济 Effects。

MVP 约束：同月只允许有限层数的因果展开；需要更细粒度的多次交互可排到下一月。必须记录这种时间分辨率带来的近似。

### 5.5 月度外部输入与结算

模拟每次推进一个月。运行开始时由外部调用方提供运行控制：可设置结束月份、一个或多个月末终止条件（例如全部贷款还清、月净现金流低于或达到指定阈值），或选择逐月决定继续/停止。条件在当月结算并生成月末快照后评估；贷款结清、负现金流、出售等事实本身不会隐式终止运行，只有明确配置为条件时才会终止。用户逐月停止是月末控制，不是领域事件触发的交互式暂停。

每个月正式生成之前，外部调用方可以更新当月/未来假设、参数及已知状态，也可以提交不变输入以连续运行。快速模式可一次启动运行并保持输入不变；完全交互模式可在月度边界询问用户是否修改输入、继续或停止。它们是应用/界面的交互策略，领域内核不区分快速或完全模式，只接收本月冻结的输入与运行控制。运行配置至少要有一种结束机制：结束月份、月末终止条件或逐月人工继续/停止。v1 不因未经配置的领域事件自动暂停，也不模拟破产/资金不足处置。月度输入和运行控制作为带生效月份、来源的版本化记录进入运行历史。

首版语义：每月结算生成月末模拟快照。用户可选择任意已有月末快照作为新模拟分支的起点，修改该点之后的参数/假设并重新运行；原分支保留，不能静默改写。重新模拟是新的随机试验，默认使用新的随机流/试验 ID，因此即使规则和参数不变，生成数据也可以不同。核心保证规则版本及其执行语义一致、输入和来源可审计，不保证结果符合现实或“看起来合理”，也不把相同输入生成相同数据作为产品不变量。只拒绝结构缺失、数值无法计算或违反账务完整性的输入；经济上不寻常的参数和结果不阻断运行。中断后恢复同一个未完成运行属于 checkpoint recovery，应避免重复提交；它与从月末快照发起的新模拟分支不同。交互式领域决策暂停不属于首版要求。

### 5.6 正常终止

每月结算和关闭完成后评估运行控制。到达 `end_month` 或满足已配置的月末终止条件时，运行正常完成；若用户在月度边界选择停止，则记录用户停止状态和月份。显式取消、输入错误或运行失败单独记录，不能与正常完成混为一类。未设置贷款结清条件时，贷款结清不会隐式终止模拟。


## 7. 业务 Slice 路线图与验收

### S1. Property Acquisition & Mortgage（第一个纵向 Slice）

**支持两种入口：**

- **New Acquisition**：购房发生于模拟内；生成购买、首付、交易费用、贷款发放及房产所有权状态变化。
- **Existing Ownership**：模拟开始时已持有；直接载入房产资产和未偿贷款的 Opening State，**不伪造购房历史**。

**状态：** 房屋持有状态、贷款余额、利率、付款金额、计息规则、剩余摊还期、利率条款到期月、付款计划、贷款状态。

**月度行为：** 计算利息、拆分本金/利息、扣除现金、更新本金；最后一期调整防止超额还本；结清时产生 `mortgage.paid_off` 事件；之后不再扣月供，但 Simulation 继续。

**边界：** 模拟一套房产；v1 支持多条相互独立的贷款记录，每条贷款有自己的本金、条款、付款计划和账簿负债科目。现实中第二抵押贷款是独立的第二笔贷款，借款人仍需偿还第一笔贷款；它不是多家银行共同分持一笔债务。[加拿大金融消费者机构说明](https://www.canada.ca/en/financial-consumer-agency/services/mortgages/borrow-home-equity.html) M2 先以一笔固定利率、固定月供的普通抵押贷款打通纵向切片，随后在 v1 内扩展并验证多笔贷款的并行演化和独立记账。抵押顺位、HELOC、加拿大式半年复利折算、续约/浮动利率、提前还款和再融资作为后续明确子里程碑；抵押顺位在涉及出售清偿前无需进入首个贷款计算模型。

**关键测试：**
- 初始余额正确；购房交易不重复入账；
- 每月 `payment = principal + interest`（按统一舍入约定）；
- 本金不为负；最终一期正确结清；
- 模拟在结清后仍运行；
- 多笔贷款分别更新本金与负债科目；结清其中一笔不影响其他贷款；
- 从贷款第 80 个月状态开始与同等条款的连续运行结果一致（在完整必要状态相同前提下）；
- 零贷款情形不产生还款。

### S2. Property Tax & Insurance

按年度、季度或月度规则产生应付/支付；首版以月度归集。税费与保险分开分类；可配置金额、周期、涨幅与起始月份。**不将年度费用默认均摊为每月真实支付**，除非选择预算化/月缴规则。

测试：不同支付周期、年界、起始月份、金额调整、与 S1 同月现金合计。

### S3. Regular Maintenance & Exterior

除草、除雪、花园维护、定期检查。规则可为季节性、周期性或状态阈值；雪量等可由简化环境变量生成。记录事件与费用；无需日级天气仿真。

测试：季节、阈值、无雪不触发阈值除雪、自动策略、费用分类。

### S4. Component Deterioration & Repair

屋顶优先；再扩展热水器、供暖、管道。状态含年龄、状况、损伤、维修历史；自然演化与随机故障分开。事件可触发修补或更换；维修完成与付款可跨月。延期维修决策属于未来扩展，不属于 v1 交互式暂停流程。维修不等于等额增加资产市场价值。

测试：故障概率、维修后状态、延期后风险、事件因果、现金和状态一致性。

### S5. Occupancy & Rental

自住/出租/空置状态，租金计划、租客搬离、重新出租、空置成本。租客离开影响后续收租规则；是否当月全额收租必须有显式政策。

测试：空置无正常租金、租约起止、状态转换、跨 Slice 影响。

### S6. Utilities & Operating Costs

水电暖、服务费用；月度固定/季节/使用量相关模型。与气温、入住状态相关，但保持模块隔离。

测试：季节性、空置用量、异常费用和模型版本。

### S7. Valuation & Disposal（可选扩展）

估值变化属于资产状态而非现金收入。出售发生时，生成成交现金流、交易费用、清偿贷款、持有状态变化；出售后停止房产运营 Slice。模拟继续至用户配置的月末终止条件、结束月份或用户停止；出售本身不是隐式终止条件。

测试：出售清算不重复记账；已出售房产不再产生物业运营事件；未配置出售终止条件时模拟继续。

### 7.1 Slice 实施原则

每完成一个 Slice，先通过独立测试，再与已有 Slice 在同一可配置运行控制下组合验证；24/240 月只是可选回归场景。避免所有 Slice 写完后才第一次整合。首个内存纵向切片包括：Scenario → S1 → Monthly Runner → Ledger → 数据集；CLI 属于核心领域和基础模拟流程完成后的应用阶段。


## 8. 事件、过程、决策与 Effects

### 8.1 事件边界

- **Process**：持续老化、计息、环境演化；不需要每月生成“老化发生”事件。
- **Event**：离散事实；如 `roof.leak_detected`、`mortgage.paid_off`。
- **Action/Decision**：用户或策略选择；如 `repair`、`replace`、`postpone`。
- **Effect**：状态修改、经济义务、现金交易、未来计划变化。

### 8.2 事件字段

```rust
struct SimulationEvent {
    id: EventId,
    period: YearMonth,
    kind: EventKind,
    source_slice: SliceId,
    subject: EntityId,
    cause_ids: Vec<EventId>,
    payload: EventPayload,
    trace: Option<EventTrace>,
}
```

建议稳定的 namespaced type ID：`mortgage.payment_completed`、`mortgage.paid_off`、`roof.leak_detected`、`maintenance.snow_removed`、`rental.tenant_departed`。事件类型与生成器一对多：同一个屋顶损坏事件可以由老化或暴风雪生成。

### 8.3 触发类型

`Scheduled`、`Periodic`、`Conditional`、`Stochastic`、`Decision`。触发机制不是互斥业务类别。

### 8.4 事件过滤原则

模拟直接影响现金、未来现金、物理/经济状态或其他重要事件条件的变化。普通晴天、植物开花等若不改变模型状态或风险，可作为环境输入而非正式事件。

### 8.5 决策策略

未来可支持 `Automatic`、`Interactive`、`ConditionalThreshold` 等决策策略，并记录请求、可选项、所选项、依据、关联事件和后续安排。交互式暂停及等待用户决策不属于 v1；v1 的决策由场景配置的自动规则处理。小额例行费用自动处理是未来策略示例，不是 v1 的通用规则。手动改变已结算历史须创建新分支，不直接改写旧记录。

### 8.6 Event Trace

可选保存模型版本、输入状态摘要、风险/阈值、随机抽样值、计算出的严重程度和成本参数。目标是规则可审计、结果可解释，而非展示伪精确的现实预测。


## 9. 随机性与概率模型

### 9.1 发生与后果分离

故障发生概率、损坏严重度、维修费用、维修持续月份应独立建模。风险不是事件；事件不等于成本。

### 9.2 首批工具

- Bernoulli：月度发生/不发生；
- Poisson：事件到达强度（适用时）；
- Weibull：年龄相关的失效时间/危险率；
- Categorical：严重程度；
- Lognormal 或有界分布：非负右偏费用；
- Scheduled/Threshold：确定性与条件事件。

Weibull 失效分布：`F(t)=1-exp(-(t/eta)^beta)`，其中 t/eta 使用一致时间单位。月度条件概率为：

`p = 1 - exp(-[((t+Δ)/eta)^beta - (t/eta)^beta])`，Δ = 1/12 年（若 t 以年计）。

**不保证**在任何有限模拟区间内一定故障（例如 20 年）；更不把 Weibull 当作物理状况的唯一老化公式。

### 9.3 共享环境与相关性

天气、通胀、入住率等由共享 Environment State 提供；多个 Slice 读取它们，因此事件可相关，但 Slice 不互相调用。环境数据可按月生成，不必每次变化都写入 Event Log。

### 9.4 随机流、回放与重模拟

记录随机算法版本、按范畴/Slice/实体/用途划分的随机流规则、模型配置、engine/ruleset/schema 版本和试验 ID。**历史回放**应用该分支保存的 Effects；**从快照重模拟**以新试验 ID 创建新随机流，允许结果不同；**checkpoint 恢复**继续同一运行，避免重复提交。固定 seed 可用于诊断、测试或明确要求复现的运行，但相同 seed 的逐项结果一致不是一般用户重模拟的产品不变量。


## 10. Ledger：必要但克制

### 10.1 为什么要 Ledger

仅有月度 `income` / `expense` 无法正确表示购房、贷款发放、归还本金、利息、维修费用与估值变化。Ledger 是经济事实层，不等于 Financial Report。

### 10.2 建议最小账户

- `CashAccount`：现金余额；
- `LoanAccount`：未偿贷款本金；
- `PropertyAsset`：房产账面/参考估值状态（明确字段语义）；
- `ExpenseCategory`、`IncomeCategory`：分类与追溯。

领域可用 typed economic effects 表达业务变化，但所有已过账的 Ledger Transaction 在 v1 必须采用借贷复式记账并满足借贷平衡。领域 Effects 与 Ledger 分录可以分层表示，不能以轻量余额变化账本替代复式账簿。

### 10.3 交易与分录

```rust
struct LedgerTransaction {
    id: TransactionId,
    period: YearMonth,
    source_slice: SliceId,
    source_event_id: Option<EventId>,
    entries: Vec<LedgerEntry>,
}

struct LedgerEntry {
    account_id: AccountId,
    side: DebitOrCredit,
    amount: Money,
    classification: EntryClassification,
}
```

每条分录的金额为非负金额，借方/贷方由独立方向字段表示；同一凭证借方合计必须等于贷方合计。账户余额方向由账户类型和科目定义，不能把带符号的业务余额变化当作复式记账分录。

例如月供 1,800，其中本金 1,250、利息 550：借记贷款负债 1,250、借记利息费用 550、贷记现金 1,800。`payment = principal + interest`，而不是把 1,800 全算作经营费用。

### 10.4 月度结算

每月保留：

- Opening balances；
- 完整交易明细；
- Operating cash inflows/outflows；
- Financing cash flows（贷款、注资等，分开分类）；
- Net cash change；
- Closing balances；
- Loan outstanding；
- World State snapshot。

公式：`closing_cash = opening_cash + sum(cash_changes)`。本项目采用月度模拟口径：模型生成的期间收入/费用，其权责发生和现金收付在同一个月度结算点处理，相关收入/费用与现金变动同月记录。这是模拟简化，不代表任何真实场景或会计/税务合规结论。首版不模拟应收应付与收付之间的时间差；未来若支持，需显式增加应收/应付状态及结算事件。现金流与非现金资产重估分开。年度费用按配置的规则入账；若模型表达年度实际支付，应在配置的月份记录，不自动均摊。

### 10.5 负现金流与家庭流动性

首版不模拟家庭整体现金、偿付能力、逾期、违约或止赎。房产相关月度净现金流允许为负；负值只表示在用户当前假设下，房产相关流出超过流入，不表示用户或家庭无力支付，也不会自动限制、暂停或终止模拟。用户可显式将负现金流或现金流阈值设为月末终止条件。CLI/GUI 可用颜色或提示文字标示负现金流，但提示属于展示层，不改变领域结果。

资金不足时的处置（例如外部注资、延迟支出或跳过维修）是可能的未来模型能力，不能作为 v1 的隐式行为。v1 不根据模拟现金余额推断用户是否实际付款，也不据此生成逾期、违约等事件。

若运行配置显式跟踪物业现金账户，该账户余额只代表模拟纳入的资金范围，不应默认解释为家庭全部可用现金。复式记账中超出所跟踪现金范围的支出对方科目，需在 Ledger 实现阶段按清晰的“范围外家庭资金/业主资金”语义处理；不得伪称为经营收入，也不得因此创建偿付能力/违约决策。首版不要求用户输入家庭全部资产和负债，只要求输入所选模拟范围内的期初账户和继续运行所需的状态。

贷款的付款计划和条款均是生成模型输入。首版不推演漏付、逾期利息、违约或止赎。若计划付款低于当期利息，按利息资本化规则更新贷款余额；这只是模型定义的结果，不表示用户漏付或违约。校验只拦截缺字段、非法数值或无法执行的计算；经济上不寻常但可计算的假设不要求用户修正。房产范围现金流为负同样只作为模拟结果输出。

### 10.6 模拟范围内的账务投影

核心可从复式 Ledger 派生所选房产模拟范围内的期初/期末资产与负债、期间收入与费用、以及现金流明细。这些是模拟数据集的投影，服务于多分支比较和外部分析；不宣称是法定/税务用途的正式财务报表，也不实现完整会计准则、IRR、NPV 或收益率 Dashboard。展示层可以选择如何呈现这些投影，外部程序可进一步分析。


## 11. 世界状态与存储

### 11.1 World State

```rust
struct WorldState {
    property: PropertyState,
    components: Vec<ComponentState>,
    occupancy: OccupancyState,
    loans: Vec<LoanState>,
    accounts: Vec<AccountState>,
    environment: EnvironmentState,
    slice_states: SliceStates,
}
```

初始状态可以从模拟中途接入，要求**充分状态**：仅知道贷款本金但不知道条款、或仅知道屋顶年龄但不知道需要的状况参数，可能不足以继续某个 Slice。

### 11.2 历史与快照

- Event Log：不可变的事件历史；
- Decision Log：选择与策略历史；
- Ledger：经济明细；
- State Effects：状态变化；
- Monthly Snapshots：至少月末状态；
- Runtime Checkpoint：用于恢复未完成月份的调度队列和必要 RNG 状态。若未来加入交互式决策，待决策状态也需纳入 checkpoint；v1 不暂停等待领域决策。

运行存档与数据导出不是同一件事：JSON 数据集可用于外部消费，但恢复精确执行还需要 runtime checkpoint。

### 11.3 持久化

SQLite 用于项目、配置、事件、流水、快照、运行状态；MVP 可先内存执行并输出 JSON，再引入 SQLite。提交必须保证事件、Effects、Ledger、快照的原子性和幂等性。

### 20.3 复式记账 domain

第一阶段采用标准借贷复式记账。余额符号统一为正数显示余额，借/贷方向由账户类型和科目定义；每张过账凭证借方合计等于贷方合计。期初状态通过期初余额/期初凭证进入账簿，并与 `InitialWorldState` 对账，不记作模拟期间收入或现金流。期初输入由用户提供所有已知资产与负债；收支参数作为未来期间生成假设，不能用来代替期初余额。

建议最小模型：

```rust
struct JournalEntry {
    account_id: AccountId,
    side: DebitOrCredit,
    amount: Money,
    classification: Option<EntryClassification>,
}

struct JournalTransaction {
    id: TransactionId,
    period: YearMonth,
    source: TransactionSource,
    entries: Vec<JournalEntry>,
    status: TransactionStatus,
}
```

本项目不是经营企业会计系统。首版以**个人/家庭持有的一套房产**为模拟主体，科目围绕房产相关资产、融资、收入与支出设计，不引入企业股本、应付工资、折旧税务申报等企业会计/税务流程。最小科目类型仍为资产、负债、权益、收入、费用；主要期初科目类别为纳入模拟范围的现金/银行等流动资产、房产参考资产、一项或多项抵押贷款及用户纳入范围的其他负债，以及用于开账平衡并与范围内净值核对的期初权益。模拟期间科目覆盖租金等收入，以及利息、物业税、保险、维护维修、水电等房产费用。若场景不含出租，租金收入科目余额为零即可。具体科目编码和细分在 Ledger 实现里确定；不得通过把贷款本金偿还记为费用来平衡现金变化。

首版先用个人/家庭主体和通用房产科目，不实现家庭持有与公司持有之间的税务、法律责任或报表差异。为未来扩展，凭证来源及可选维度应能标识持有主体/物业/用途，且科目定义不与某个 GUI 表单绑定；将来如公司持有需要不同科目表、权益结构或税务处理，再通过版本化的 `AccountingProfile`/科目表扩展，而不是把企业规则塞进个人科目。期初借贷差额通过明确的期初净值/权益来源平衡，并能与用户提供的资产负债和净值事实核对，不得用不透明的“杂项收入”抹平差额。

需先写会计 ADR 和逐笔分录样例，至少包括：期初余额、购房及贷款发放、首付、月供（本金/利息拆分）、维修费用、租金收入、税费缴付和用户注资。资产负债表、利润表、间接/直接现金流展示口径及现金流分类要在投影 API 中明确；报表是从已过账分录推导的视图，不是另行维护的第二套事实。

**账务不变量**：每张已过账凭证借贷平衡；科目余额可由期初余额加已过账分录重算；现金余额与世界状态中的现金账户一致；贷款负债余额与贷款 Slice 状态一致；每项经济 Effect 可追溯到凭证；撤销或更正使用反向/调整凭证，不静默改写已过账历史。期间结账需要幂等保护，禁止重复提交。


### 20.4 利息与抵押贷款 domain

首个完整 Slice 为单笔抵押贷款，覆盖已存在贷款和模拟内新建贷款两种路径；v1 后续扩展为多笔独立贷款并行运行。首版规则为：名义年利率除以 12 得到月利率、对月初本金计整月利息、月末付款先付利息再还本金、利息按货币最小单位四舍五入。付款低于利息时，差额按模型规则资本化；贷款 ADR/测试向量需记录该边界的数值向量。其他待定实现细节限于条款生效月份及极端输入校验；所有示例和 golden fixture 使用明确的 convention ID 与版本。

首版计算如下。设月初贷款余额为 `B_m`，名义年利率为 `r`，当月付款计划为 `P_m`，则月利率 `j = r / 12`，当月利息 `I_m = round_currency(B_m × j)`；实际付款 `A_m = min(P_m, B_m + I_m)`；实付利息 `J_m = min(A_m, I_m)`；偿还本金 `Q_m = max(0, A_m - I_m)`；资本化利息 `C_m = I_m - J_m`；月末贷款余额 `B_(m+1) = B_m + C_m - Q_m`。因此当 `P_m < I_m` 时，差额按模型规则资本化，贷款余额增加；这不表示漏付或违约。付款大于结清所需金额时，最后一期调整为 `A_m = B_m + I_m`，从而 `Q_m = B_m`，避免超额还本。`round_currency` 按币种最小单位四舍五入，正数中点采用 half-up；内部中间计算保留足够十进制精度。

月度顺序固定为：月初读取本金与当月生效条款 → 计提整月利息 → 月末付款分配（利息优先、本金其次）→ 产生凭证与贷款状态 Effect → 检查结清并发出事件。该规则不支持日级部分月份；新贷款或条款变更首版须从月初生效。

**算法替换边界：** 贷款 Slice 依赖领域策略接口，而不内嵌具体利息公式。概念接口可为 `InterestAccrualConvention::accrue(opening_balance, terms, period) -> Result<Money, DomainError>`，还款分配使用独立的 `PaymentAllocationPolicy`（首版实现 interest-first）。接口结果由贷款 Slice 转成状态 Effects 和 Ledger 凭证；策略本身不写总账、不访问 UI/存储，也不直接更改共享状态。Scenario 保存 `interest_convention_id`、版本和完整参数快照；历史回放使用保存的 Effects，快照分支按当前选择的规则版本继续生成。同一软件/模型版本内规则/输入解释一致；随机生成数据可因新试验流而不同。不保证应用升级后旧数据自动迁移或旧算法仍可执行。替换算法时新增 convention 实现和版本、对应测试向量；破坏性数据/schema 更新允许由升级覆盖，是否提供导出备份由应用层决定。只有当算法差异改变业务语义（例如日计息或欠息资本化）时，才扩充策略输入/输出契约。

每笔贷款最低状态包括期初本金、年利率、付款计划、还款日/月、贷款生命周期状态，以及续跑所需条款。月度计算拆分本金和利息；利息费用计入利润表，支付时减少现金；偿还本金减少现金与贷款负债，不计入费用。最后一期不得超额还本。v1 先实现固定利率/固定付款，再支持多笔贷款并行；续约、浮动利率、提前还款和不同司法辖区计息规则后续扩展。

贷款数学测试不仅测试最终余额，也测试逐月利息、还款拆分、资本化利息、余额演进及每一笔凭证。测试向量包括零利率、正常利率、极小余额、付款低于/等于/高于利息、刚好结清、超额付款封顶和无贷款场景。


### 20.5 随机模型、试验流与分支

随机性属于核心 domain，第一阶段即纳入，不等到后续 Slice 完成后再补。随机模型按模拟范畴归属和版本化，首批范畴为：

- **自然环境**：天气/季节等外生环境变量；首版可以简化或配置驱动，不要求日级天气。
- **房屋与组件状态**：老化、磨损、故障风险、维修成本等物理过程。
- **国家/地区政策与宏观条件**：物业税规则、保险/监管参数、利率路径及通胀等；政策输入可为固定情景，也可在明确模型后随机生成。
- **居住与运营过程**：入住、租客搬离、空置及使用量等行为过程，可在对应 Slice 实施时纳入。

这些范畴是领域归属，实际模型可拆成多个 Slice。这里要区分两个概念：**分布/生成模型**定义抽样值的概率含义与形状（如 Bernoulli、Weibull 条件故障概率、右偏维修费用）；**随机流策略**定义这些模型如何从伪随机数生成器取得随机输入，以及各自如何在新分支、增加 Slice 和 checkpoint 恢复时保持边界清晰。

**首版相关性边界：** 自然环境、房屋/组件状态、政策/宏观条件、居住/运营过程这四类随机范畴各自组织模型和随机流；范畴间暂按独立处理，不实现共享潜变量、相关矩阵或因果相关抽样。该选择是首版简化假设，不声称现实世界变量互相独立，也不要求现在提供校准数据。Slice 可以读取明确生成的环境/政策状态作为输入，但不得暗中引入跨范畴随机相关。只有具体模型表明相关性确有必要时，才增加版本化相关机制并说明依据、输入和测试；不为假想需求预建相关性框架。首阶段先实现随机流协议和一个代表性概率模型（建议组件故障危险率/Weibull 条件月概率），验证抽样和分支行为。

- 保存随机试验 ID；可选记录主 seed、PRNG 算法及版本、模型版本、参数来源/状态（demonstration、estimated、calibrated、user_defined）。试验 ID 用于区分从同一场景或快照创建的独立随机轨迹。
- 随机流按稳定键派生，例如 trial ID/可选 seed + 随机范畴/Slice ID + 实体 ID + 随机用途 + 模型版本；同一 trial 内的流划分应避免无关 Slice 共享同一消费序列。随机流策略不是概率分布本身，而是分配随机输入的机制。首版不同范畴的流相互独立；是否引入跨范畴相关性由未来显式、版本化的模型决定。
- 可采用计数器式抽样或持久化流状态；checkpoint 恢复同一运行时延续该 trial。用户从月末快照重新模拟则创建新的 trial，不要求新旧分支的随机结果相等。
- 每次随机抽样的语义输入、概率/分布参数、结果和来源要可审计；不要求把共享环境每月每个数值都建成业务事件，但需能重建或保存影响结果的环境状态。
- 固定 seed 可用于确定性测试/诊断；产品的普通“从快照重新模拟”生成新试验流，允许结果变化。统计测试验证抽样符合数学定义的容许范围；统计正确性不等于现实校准有效性。
- Monte Carlo 扩展可对同一基础场景创建多个独立 trial ID/seed，每个 trial 按相同规则和参数运行，再由独立分析层汇总结果；首版只提供试验身份和随机流边界，不实现批量调度或统计报告。
- 规则一致性不变量：一个 trial 固定 engine/ruleset/model 版本；每个月的有效参数快照明确记录。只改参数时执行同一版本规则；若用户选择新规则版本，则这是显式的新规则配置。新 trial 可以在同一规则/参数下抽出不同随机轨迹。


### 20.6 月度生命周期与 Slice 组合

核心协调器实现 Input → Open → Context → Evolve/Accrue → Propose → Resolve → Commit → Close。首版不暂停等待领域决策；外部输入在每月 Input 阶段更新并冻结。接口仍支持依赖声明、稳定排序、有限层同月因果展开和原子提交。

Slice 契约至少声明 ID/模型版本、所需输入、依赖、读取/写入资源、配置校验和提案函数。统一提交器检查同一实体的冲突写入；现金变化通过凭证汇总入账，贷款本金、占用状态、组件状况等由领域规则串行处理或冲突报错，不能盲目相加。

首阶段组合顺序：

1. 贷款 + 复式 Ledger（最小纵向闭环）。
2. 加一个确定性周期 Slice（税费或保险），验证同月多凭证和现金流分类。
3. 加一个随机组件风险 Slice，验证共享状态、风险模型、维修 Effect 与费用凭证。
4. 用上述组合验证保存快照、跨段续跑、历史审计与重放。

租赁和未来可能需要的交互式决策能力在依赖协议验证后加入；首版核心运行不暂停。界面不作为领域验证依赖。每个 Slice 使用短期确定性案例、边界测试和组合不变量；24/240 月是可配置的回归样例，按风险选择，不要求每个小改动都跑固定 240 月。
