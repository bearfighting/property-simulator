# 实施路线与里程碑

> 本文保留原规范章节编号，便于和既有讨论对应。本文是当前里程碑与实施顺序的权威来源；领域定义见 [domain-model.md](domain-model.md)，工程门槛见 [engineering-practices.md](engineering-practices.md)。

## 20. 实施计划 v0.5：领域内核优先

本节把 v0.4 的架构原则转成可执行计划。若本节与第 15、19 节的旧里程碑排序冲突，以本节为准；业务边界以 [产品概览](overview.md) 和 [领域模型](domain-model.md) 的当前基线为准，已确定的设计方向见 [ADR 归档](adr/README.md)。CLI 和 GPUI 是后续应用层，不是第一阶段交付目标。第一阶段以可组合领域模型、数学定义、状态连续性和账务正确性为核心，并用单元及集成测试验证。

### 20.1 首阶段设计目标

首阶段完成一个可独立使用的 Rust domain/core 库，能够：

1. 描述任意有效起始期的充分状态，包括用户事实、此前生成且仍影响未来的状态，以及继续演化所需的规则/随机过程状态；审计历史单独保存，不作为隐式计算输入。
2. 以“完整期初状态 + 当期冻结输入 + 当期随机输入 → 当期结果 + 期末状态”定义单期转移；由更高层运行控制重复调用并决定何时停止。
3. 保存每月末快照并从任意月份创建新模拟分支；同一未完成运行的 checkpoint 恢复不重复提交。新分支可使用新随机试验流，不要求与原轨迹一致。
4. 组合至少两个 Slice，并显式处理依赖、同月先后顺序、资源冲突及跨 Slice 经济影响。
5. 以复式记账保存经济事实，并从总账推导资产负债表、利润表和现金流视图。
6. 输出可比较的内存数据集/测试 fixture；应用界面和文件导出不属于本阶段完成条件。

240 个月是一个长期回归场景，不是模拟固定长度或领域 API 的约束。所有区间均由起止年月指定，允许从任意有效月份开始或分段延续。

可扩展性是首阶段的首要设计约束：新增初始配置参数或 Slice，应通过增加领域类型/配置字段、校验和相应策略实现完成，避免重写运行器、Ledger 或上层应用。扩展性不等于预先实现通用 DSL/插件系统；抽象必须对应已知变化边界并可测试。


### 20.7 分阶段里程碑与验收

**M0 — 设计决策与可运行骨架**

M0 的目标是让团队可以安全开始 M1 领域实现；它建立工程约束、模块边界和决策记录，不在此阶段实现完整 Ledger、贷款模型、CLI 或 GUI。

**M0 checklist**

- [x] **确认范围基线**：以产品概览和领域模型为准，确认月度模拟、个人/家庭持有一套房产且 v1 支持多笔独立贷款、用户指定时长、月初输入、月末快照分支、新 trial 可重新抽样、负物业现金流可继续、不模拟破产/资金不足处置/逾期/违约/止赎、不将生成记录视为真实行为或法定会计记录、升级可破坏性更新等边界；多笔贷款由同一贷款规则实现逐笔处理，彼此独立。暂停决策、资金不足处置、现实性判断和固定期限均非 v1 约束；若未来纳入，须作为显式设计扩展。
- [x] **确定最小工程骨架**：选择 Rust 2024 edition、stable toolchain 和 Cargo workspace；建立 domain、accounting、simulation、models 四个最小 crate，并在架构文档明确职责及依赖箭头。尚无职责的 Infrastructure、CLI 和 GUI crate 暂不创建。
- [x] **建立 ADR 工作方式**：`docs/adr/` 有模板、编号约定和 ADR-01 至 ADR-17；每份记录状态、背景、决策、备选方案、后果及测试向量或说明不适用。
- [x] **完成 Ledger 基线 ADR**：说明首版个人/家庭账户类别、借贷方向、期初净值核对、收入费用分类和同月权责/现金简化，并给出开账、月供、维修、租金、税费及欠息资本化分录向量。
- [x] **完成贷款利息 ADR**：锁定年利率除以 12、月初余额计息、月末利息优先、欠息资本化、末期付款封顶、十进制中间精度和最终按分 half-up 舍入；明确生效月份、非法输入和边界向量。
- [x] **完成随机与分支 ADR**：记录四个随机范畴及暂定独立假设、`trial_id`/seed/版本职责、分支和 checkpoint 语义；PRNG/派生算法留待 M3。
- [x] **完成配置与运行控制约定**：记录初始配置、运行控制和月度输入快照，含包含端点、终止 OR 语义、月末评估、生效月份、校验/来源追踪及历史快照分支规则。
- [x] **确定质量工具链**：`scripts/check.sh` 统一执行 `cargo fmt --all --check`、workspace Clippy（`-D warnings`）、workspace 编译和测试；GitHub Actions push 与 pull request 均调用该入口。warning 视为失败，lint allow 仅在有明确理由时局部使用。
- [x] **建立分层测试布局**：工程规范确定 domain 单元测试、application fake/in-memory 测试和后续 infrastructure 集成测试；固定 seed 仅用于测试/诊断。Ledger 与 mortgage 手算向量见 [test-vectors.md](test-vectors.md)。
- [x] **验证空骨架**：运行统一脚本验证 workspace 格式、lint、编译和测试；crate 依赖方向及职责见架构文档。此项仅验证工程骨架，不代表其余 M0 工作完成。

**M0 交付物**：最小可编译 Rust 工程、分层/依赖说明、ADR 模板及关键 ADR、质量命令/CI 配置、Ledger 与 mortgage 测试向量清单。

**M0 完成条件**：checklist 中所有首阶段必做项完成；关键领域语义没有相互矛盾；Ledger 与贷款公式有可手算凭证/数值样例；新成员可按文档运行质量命令并知道新增代码应放在哪一层。M0 不要求完成真实领域计算。

**M1 — 原语与 Ledger**

按以下顺序完成；后续任务依赖前面的类型与不变量：

- [x] **M1.1 基础值与标识类型**：在 `domain` 实现 `YearMonth`、带币种代码的十进制定点 `Money`、舍入策略及强类型不透明 ID。ID 由调用方提供，重试复用原 ID；Ledger 单币种约束由 M1.4 的 Ledger 承载。
- [x] **M1.2 科目表与分类**：在 `accounting` 定义账户类别、由类别决定的正常余额方向、`AccountCode` 分段/排序、账户唯一性与有效性校验，以及直接现金流分类。代码仅用于识别、分组和排序，不决定借贷行为。
- [x] **M1.3 期初余额和余额推导**：实现期初账户余额记录与资产、负债、权益核对；期初事实不创建模拟期间凭证或现金流。允许净资产为负，只要开账借贷平衡；账户余额由期初余额推导。
- [x] **M1.4 复式凭证过账**：实现交易与分录的结构校验、账户引用和币种校验、非负分录金额、借贷平衡校验、过账状态及余额重算。拒绝不平衡或重复交易 ID；不得将本金还款记作费用。
- [x] **M1.5 财务投影**：从期初余额和已过账分录推导账户余额、资产负债表、利润表及直接法现金流（经营/投资/融资）。不维护平行手写合计；非现金资本化不进入现金流。
- [x] **M1.6 向量与里程碑验收**：将 [Ledger 测试向量](test-vectors.md#ledger-vectors)落实为 domain/accounting 测试；覆盖开账、凭证平衡/拒绝、余额重算、负净资产、币种不匹配、现金流分类和报表对账，并运行 `./scripts/check.sh`。

**M1 完成条件**：M1.1–M1.6 全部完成；期初资产/负债不变成期间流水；现金、贷款、权益、损益与现金流投影可从账簿对账。M1 不实现贷款利息计算（属于 M3），也不实现月度运行器（属于 M3）。

**M1 按有效输入无运行时失败原则复核（M2 前跟进）**

M1 原验收证明了账务不变量和拒绝非法凭证；此项复核进一步区分输入边界校验与有效模拟结果，避免把模拟过程中的可计算结果当成运行错误。此复核不撤销 M1 已完成状态，但复核发现的领域规则缺口须在依赖它的 M2/M3 实现前解决，并同步更新 ADR、向量和测试。

- [x] **分类 M1 错误边界（历史复核，2026-10-19）**：复核曾发现现金分类、投影前置条件和金额累计溢出可能延迟到计算阶段。后续整改已在交易提交时验证现金分类、通过 `ValidatedProjection` 前置检查投影范围与现金账户，并将有限 `i128` 的超界行为明确为 checked numeric error；当前实现以 ADR-19 和下方完成项为准。
- [x] **确认验证错误边界（历史复核，2026-10-19）**：复核确认可修正结构问题应在场景/期初/月度冻结/提交前验证，内部不变量破坏或基础设施故障不能归类为用户输入问题。验证边界与有限数值范围的最终契约见 ADR-19；当前 M1 实现状态见下方整改项。
- [x] **实现负现金头寸及 L-08 连续性**：科目可显式标记为 cash-position；仅该类资产允许贷方余额。跨月测试验证余额、资产/权益、净收入和现金流对账，不生成隐含融资活动。
- [x] **确定金额表示范围（2026-10-19）**：采用 `i128` 十进制系数与显式 scale（最多 28 位），不要求无限精度。超出表示范围或 checked 运算溢出会明确报错；不截断或回绕。金额仍须在合理输入边界校验，极端不现实的计算溢出可显式失败。
- [x] **复核投影前置条件并前移验证**：账簿按科目表的 cash-position 标记固定现金账户集合；交易提交时检查现金科目必须带分类、非现金科目不得带分类。`validate_projection()` 返回借用账簿的 `ValidatedProjection`，在调用 `project()` 前检查区间和配置一致性；有效投影只执行计算。
- [x] **完成 M1 实现整改与验证**：负现金头寸、开放年份类型、有界 `i128` Money、交易分类校验和独立投影验证结果已实现。测试覆盖跨账户、跨月的大额资产、累计净收入和现金流投影，以及 L-08 连续性与输入验证前置。超出数值表示范围的 checked overflow 是明确错误，不要求任意精度。单期充分状态/历史独立性测试随 M2 转移接口实现，不属于 M1 Ledger 原语验收。

**本次复核结论与下游顺序（2026-10-19）**：M1 复核整改现已落实于值对象、Ledger、投影验证入口和相关测试。单期充分状态及历史独立性契约见 ADR-18，并由 M2 单期转移测试落实；运行期限和停止条件仍由更高层运行控制负责。M3 贷款 Slice 沿用相同金额表示与现金账户/分类验证。负物业现金流继续是正常输出，不触发模拟终止或偿付能力处置。

**M2 — 月度活动与 Slice 基础**

- 以 ADR-18 的充分状态契约作为 Slice 输入边界：每个规则只读取显式期初状态、本期输入、随机输入及明确传入的同月阶段结果；若规则需要历史影响，将其保存为显式续行状态，不扫描审计事件日志。运行期限和停止决策留在单期计算之外。
- 明确每月先接收用户输入：用户可更新从本月生效的状态/未来参数，也可新增或调整会带来现金流变化的活动实例；输入冻结后，再计算本月所有生效活动。
- 定义通用活动计算边界：Slice 是计算规则/代码边界，按配置处理生效的活动实例并产生事件、状态 Effects 和复式 Ledger 交易。Slice 实现与活动实例不要求一一对应；一个实现可处理多个实例，也不要求把多种活动塞进一个大 Slice。Slice 不直接修改共享状态或 Ledger。
- 明确一个月内各生效活动的结果如何汇集：现金变动按账户和现金流分类累计；非现金状态 Effects 按实体/资源规则处理；完整活动明细与来源保留，不能只留下月度净额。统一提交必须将状态 Effects、事件和 Ledger 交易作为一个原子单元。
- 规定概率模型如何为活动提供本月结果：模型按配置判断活动本月是否发生并给出发生值/金额，所属计算规则将结果转成该月活动记录和必要的状态/账务影响。模型不直接写共享状态或总账。
- 对输入边界接受的配置，确定性计算和所有有效随机结果都必须能产生模拟输出；输入范围、分布支持范围、账务约束及数值可表示性在运行前或月度输入冻结前校验。不得把某个有效抽样结果、负现金流或模型结果与状态的冲突留作正常运行错误。
- M1 已确定负现金及 `i128` 金额边界：cash-position 可保留贷方负余额，不推断融资；超出有限表示范围的计算显式报数值错误。M2 应在输入冻结时验证模型配置及允许抽样结果处于可表示范围；在此范围内若仍发生溢出、账务拒绝或无法解决的冲突，应视为领域设计/实现缺陷并修正。
- 以小型确定性活动与一个概率活动验证这些通用边界及可对账的月度现金流汇总；M2 概率活动可注入已确定的抽样结果，随机流分配留到 M3；不在本里程碑实现贷款专属规则、完整月度运行生命周期或通用 DSL/插件框架。
- 验收：活动来源与事件、Effects、凭证可追溯；多项现金流能在同月合计且按经营/投资/融资分类；非现金 Effect 不误入现金流；有效输入均产生输出。另以故障注入验证意外提交失败不会部分写入；该路径是完整性防护测试，不是有效输入下的预期领域结果。

**M3 — 月度运行、随机流与首个领域 Slice**

- 实现逐月运行器、可选结束月份、月末终止条件、月度继续/停止控制、月末快照、从快照创建新分支、checkpoint 恢复及随机流派生；基于 M2 的活动契约实现贷款 Slice，验证它与其他现金流活动经同一提案、提交和投影路径进入月度结果。
- 同一贷款 Slice 实现处理多笔彼此独立的贷款实例，每笔分别保存条款和余额；不建立贷款间的相关性或联动规则。已有贷款余额是期初事实，不生成模拟前放款交易；模拟期新增贷款按用户提供的用途/资金流向形成相应状态和账务结果，不推断借款所得必然进入模拟现金账户或用于房产。计息/付款分配遵循 ADR-14。
- 实现首个随机风险模型，验证其抽样结果可由 Slice 转换为当期活动并参与同月结果汇总。
- 验收：日期到期或显式终止条件在月末快照生成后触发正常完成；负现金流、贷款结清和出售在未配置为条件时不终止；月度外部停止不重复过账并保留已完成月份快照；恢复同一个未完成运行不重复过账；从任意月末快照创建分支后，父分支历史不变；新分支使用新试验 ID；固定 seed 能用于测试抽样协议；加入独立 Slice 不改变已有随机范畴的流分配。
- 贷款验收：M-01–M-11 全部通过；每月利息、实付利息、本金、资本化金额和期末余额一致；结清后仍可推进时间；贷款现金流与其他 Slice 的当月活动正确合计；贷款状态与 Ledger 负债对账。
- 为未来 Monte Carlo 保留“相同输入配置 + 不同 trial ID/随机流”接口；实际批量试验管理和统计汇总可后续实现。

**M4 — 多 Slice 协调**

- 加入确定性运营和随机活动实现；为活动间依赖、资源冲突和有限同月因果定义确定性处理规则，无法接受的组合在运行前校验拒绝，不在有效运行中临时失败；并与 M3 的多笔独立贷款实例组合验证。
- 验收：同月顺序可解释且稳定；多笔贷款分别维护条款、本金和负债科目，支付金额按各自计划计算；结清一笔不影响其他贷款；活动之间只通过显式状态/规则发生影响，不建立贷款间相关性；重复提交被拒或幂等；状态与 Ledger 对账；来源链完整。

**M5 — Core 稳定与数据契约**

- 固化公开领域 API、序列化 schema、模型版本策略及完整运行数据集结构。
- 允许应用升级采用破坏性数据/schema 更新；首版不承诺跨版本向后兼容或自动迁移。升级前可由应用提示导出/备份，具体机制属于应用层决定。
- 验收：完整配置、启动时运行控制与历史可保存读取；校验器能检测不连续月份、重复 ID、非法引用、账务不平和状态/账簿差异；月度输入及终止条件评估有生效时间和来源记录。

**Phase II — 应用与持久化**

- 在核心库稳定后提供 CLI，先用于批量运行和诊断；接入 SQLite 项目存储、运行恢复、导出 JSON/CSV/XLSX，以及每月输入更新工作流。
- CLI 不承载领域规则，所有计算调用 core API。验收是可从配置执行、保存/恢复并导出完整数据集。

**Phase III — GPUI 桌面应用**

- 提供 Scenario Builder、时间线、事件/决策检查、账簿探索、保存和导出。
- UI 仅通过应用接口创建配置和控制运行；后台执行不阻塞界面。验收按原第 14 节产品工作流执行。


### 20.8 测试策略

- 数学单元测试：贷款公式、概率/危险率、舍入、报表映射和借贷平衡。
- 状态机测试：任意合法起点、起止月份边界、月末关闭、结清后继续。
- 连续性测试：同一 trial 的完整运行与多个切分点 checkpoint 恢复逐项比较历史、账簿、状态和随机生成结果；从快照新建 trial 则不要求轨迹相同。
- 组合测试：Slice 顺序稳定性、冲突行为、同月因果、统一提交和幂等。
- 属性/不变量测试：借贷平衡、现金对账、贷款非负、期间连续、ID 唯一、来源引用有效。
- 固定 seed golden fixture 用于模型版本回归；统计性质测试使用固定 seed 集合与有容差的显著性界限，避免脆弱的单次随机断言。
- 测试覆盖不同持续时间，但不存在“模拟必须运行 240 个月”的业务断言。


### 20.9 已确定基线与后续技术决策

以下原则已由项目方向确定，不再作为启动编码的开放问题：

1. 月利率首版按名义年利率除以 12，按月初余额计息，月末先付利息再还本金；中间计算保留十进制定点精度，仅最终需入账金额按币种最小单位 half-up 舍入。付款低于利息时，差额按模型规则资本化并增加贷款余额；不模拟漏付、逾期或违约。精确定义见 [ADR-14](adr/ADR-14-mortgage-interest.md)。
2. 首版复式账簿以个人/家庭持有一套房产为模拟主体，期初只需覆盖用户纳入该模拟范围的资产、负债和期初净值，不要求家庭完整资产负债表；月度现金流由当月生效活动逐项产生并按账户/分类汇总，Slice 实现与活动实例不要求一一对应。v1 支持多项互相独立的贷款，M3 验证其共享同一贷款计算实现且分别演化。具体科目编码、现金流分类和开账校验细节在 Ledger 实现阶段通过样例与测试确定。负物业净现金流是模拟结果，不代表家庭偿付能力，也不暂停模拟。
3. 随机模型按自然环境、房屋/组件、政策/宏观、居住/运营四类组织；首版范畴间独立处理。仅在具体模型证明有必要时再设计相关性。
4. 每月末产生完整模拟快照；用户可从任意快照创建新分支并重新抽样。父分支保留；新分支规则与参数可审计，抽样结果不要求和原分支一致。
5. 首版不保证应用升级后的数据向后兼容。相同分支的 checkpoint 恢复需避免重复提交；checkpoint 的精确持久化格式、故障重试细节在运行存储阶段定。

已接受的细节见 [ADR 归档](adr/README.md) 与 [测试向量](test-vectors.md)。遇到真实模型需求时通过新 ADR 版本化演进，不为假想需求提前构建通用规则语言或相关性插件框架。
