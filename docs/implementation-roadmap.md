# 实施路线与里程碑

> 本文保留原规范章节编号，便于和既有讨论对应。本文是当前里程碑与实施顺序的权威来源；领域定义见 [domain-model.md](domain-model.md)，工程门槛见 [engineering-practices.md](engineering-practices.md)。

## 20. 实施计划 v0.5：领域内核优先

本节把 v0.4 的架构原则转成可执行计划。若本节与第 15、19 节的旧里程碑排序冲突，以本节为准；业务边界以 [产品概览](overview.md) 和 [领域模型](domain-model.md) 的当前基线为准，已确定的设计方向将在 M0 通过正式 ADR 记录决策细节。CLI 和 GPUI 是后续应用层，不是第一阶段交付目标。第一阶段以可组合领域模型、数学定义、状态连续性和账务正确性为核心，并用单元及集成测试验证。

### 20.1 首阶段设计目标

首阶段完成一个可独立使用的 Rust domain/core 库，能够：

1. 描述任意有效起始月份的完整已知状态，包括用户输入、之前生成的状态与历史，以及继续演化所需的随机过程信息。
2. 在给定某一时点状态时，计算该时点的确定性派生值和随机候选结果；在给定月度区间时，逐月生成结果。
3. 保存每月末快照并从任意月份创建新模拟分支；同一未完成运行的 checkpoint 恢复不重复提交。新分支可使用新随机试验流，不要求与原轨迹一致。
4. 组合至少两个 Slice，并显式处理依赖、同月先后顺序、资源冲突及跨 Slice 经济影响。
5. 以复式记账保存经济事实，并从总账推导资产负债表、利润表和现金流视图。
6. 输出可比较的内存数据集/测试 fixture；应用界面和文件导出不属于本阶段完成条件。

240 个月是一个长期回归场景，不是模拟固定长度或领域 API 的约束。所有区间均由起止年月指定，允许从任意有效月份开始或分段延续。

可扩展性是首阶段的首要设计约束：新增初始配置参数或 Slice，应通过增加领域类型/配置字段、校验和相应策略实现完成，避免重写运行器、Ledger 或上层应用。扩展性不等于预先实现通用 DSL/插件系统；抽象必须对应已知变化边界并可测试。


### 20.7 分阶段里程碑与验收

**M0 — 设计决策与可运行骨架**

M0 的目标是让团队可以安全开始 M1 领域实现；它建立工程约束、模块边界和决策记录，不在此阶段实现完整 Ledger、贷款模型、CLI 或 GUI。

**M0 checklist**

- [x] **确认范围基线**：以产品概览和领域模型为准，确认月度模拟、个人/家庭持有一套房产且 v1 支持多笔独立贷款、用户指定时长、月初输入、月末快照分支、新 trial 可重新抽样、负物业现金流可继续、不模拟破产/资金不足处置/逾期/违约/止赎、不将生成记录视为真实行为或法定会计记录、升级可破坏性更新等边界；贷款 Slice 先以一笔固定贷款打通，再在 v1 内完成多笔贷款支持。暂停决策、资金不足处置、现实性判断和固定期限均非 v1 约束；若未来纳入，须作为显式设计扩展。
- [x] **确定最小工程骨架**：选择 Rust 2024 edition、stable toolchain 和 Cargo workspace；建立 domain、accounting、simulation、models 四个最小 crate，并在架构文档明确职责及依赖箭头。尚无职责的 Infrastructure、CLI 和 GUI crate 暂不创建。
- [ ] **建立 ADR 工作方式**：创建 `docs/adr/` 模板和编号约定；每份 ADR 写明状态、背景、决策、后果和关联测试向量。把已定方向记录下来，未定的实现参数清楚标为后续决策，避免 ADR 与计划正文互相矛盾。
- [ ] **完成 Ledger 基线 ADR**：说明首版个人/家庭账户类别、期初资产/负债/权益的借贷方向、期初净值核对、收入费用分类，以及“期间权责与现金同月发生”的模拟简化。至少写出期初开账、抵押贷款月供、维修支出、租金收入、税费支出的平衡凭证样例。
- [ ] **完成贷款利息 ADR**：锁定月利率 `annual_rate / 12`、月初余额计整月利息、月末利息优先付款、未覆盖利息资本化、最后一期不超额还款、按分四舍五入；列出条款生效月份、结构性非法输入和边界数值的处理约定。给出逐月本金/利息/资本化金额/余额手算向量。
- [ ] **完成随机与分支 ADR**：固定自然环境、房屋/组件、政策/宏观、居住/运营四个范畴及范畴间暂按独立的假设；定义 `trial_id`、可选 seed、模型/规则版本的概念职责。写明快照分支保留父历史并产生新随机试验；checkpoint 恢复同一运行且不得重复提交。随机流具体 PRNG/派生实现可留到 M3 选择。
- [ ] **完成配置与运行控制约定**：定义 Scenario 初始配置、启动时运行控制、每月输入快照的关系，明确可选结束月份/月末终止条件/逐月继续或停止、多个终止条件的组合语义与月末评估时点，以及输入生效月份、必填字段校验职责和来源追踪；用户修改过去快照时创建新分支，不静默改写已有分支。
- [x] **确定质量工具链**：`scripts/check.sh` 统一执行 `cargo fmt --all --check`、workspace Clippy（`-D warnings`）、workspace 编译和测试；GitHub Actions push 与 pull request 均调用该入口。warning 视为失败，lint allow 仅在有明确理由时局部使用。
- [ ] **建立分层测试布局**：确定 domain 单元测试、application fake/in-memory 测试和后续 infrastructure 集成测试的组织约定；固定 seed 仅用于测试/诊断 fixture，不将随机轨迹重现作为产品要求。列出 M1/M2 首批测试向量，不必在 M0 实现所有测试。
- [x] **验证空骨架**：运行统一脚本验证 workspace 格式、lint、编译和测试；crate 依赖方向及职责见架构文档。此项仅验证工程骨架，不代表其余 M0 工作完成。

**M0 交付物**：最小可编译 Rust 工程、分层/依赖说明、ADR 模板及关键 ADR、质量命令/CI 配置、M1/M2 测试向量清单。

**M0 完成条件**：checklist 中所有首阶段必做项完成；关键领域语义没有相互矛盾；Ledger 与贷款公式有可手算凭证/数值样例；新成员可按文档运行质量命令并知道新增代码应放在哪一层。M0 不要求完成真实领域计算。

**M1 — 原语与 Ledger**

- 实现 YearMonth、金额/货币、舍入、ID、科目表、期初余额、凭证过账、余额重算和基本财务投影。
- 验收：无效日期/金额被拒；借贷不平衡不可过账；余额重算稳定；期初资产/负债不变成期间流水；现金、贷款和权益可对账。

**M2 — 贷款/利息 Slice**

- 实现新贷款与已有贷款起点，按已锁定规则逐月计息还款，生成事件、Effects、凭证和快照。
- 验收：所有边界利息向量通过；每月付款、本金和利息一致；余额不为负；结清后仍可推进时间；初始贷款不伪造历史发放交易。
- M2 先实现一笔固定贷款作为纵向切片；多笔贷款扩展属于 v1 必做范围，纳入 M4 组合验收。

**M3 — 时间生成、随机模型与快照分支**

- 实现逐月运行器、可选结束月份、月末终止条件、月度继续/停止控制、月末快照、从快照创建新分支、checkpoint 恢复、随机流派生和首个随机风险模型。
- 验收：日期到期或显式终止条件在月末快照生成后触发正常完成；负现金流、贷款结清和出售在未配置为条件时不终止；月度外部停止不重复过账并保留已完成月份快照；恢复同一个未完成运行不重复过账；从任意月末快照创建分支后，父分支历史不变；新分支使用新试验 ID；固定 seed 能用于测试抽样协议；加入独立 Slice 不改变已有随机范畴的流分配。
- 为未来 Monte Carlo 保留“相同输入配置 + 不同 trial ID/随机流”接口；实际批量试验管理和统计汇总可后续实现。

**M4 — 多 Slice 协调**

- 加入一个确定性运营 Slice 和一个随机 Slice；完成依赖/资源冲突/有限同月因果处理，并支持多笔独立贷款记录并行演化。
- 验收：同月顺序可解释且稳定；多笔贷款分别维护条款、本金和负债科目，支付金额按各自计划计算；结清一笔不影响其他贷款；重复提交被拒或幂等；状态与 Ledger 对账；来源链完整。

**M5 — Core 稳定与数据契约**

- 固化公开领域 API、序列化 schema、模型版本策略及完整运行数据集结构。
- 允许应用升级采用破坏性数据/schema 更新；首版不承诺跨版本向后兼容或自动迁移。升级前可由应用提示导出/备份，具体机制属于应用层决定。
- 验收：完整配置、启动时运行控制与历史可保存读取；校验器能检测不连续月份、重复 ID、非法引用、账务不平和状态/账簿差异；月度输入及终止条件评估有生效时间和来源记录。

**Phase II — 应用与持久化**

- 在核心库稳定后提供 CLI，先用于批量运行和诊断；接入 SQLite 项目存储、运行恢复、导出 JSON/CSV/XLSX，以及每月输入更新工作流。
- CLI 不承载领域规则，所有计算调用 core API。验收是可从配置执行、保存/恢复并导出完整数据集。

**Phase III — GPUI 桌面应用**

- 提供 Scenario Builder、时间线、事件/决策检查、账簿探索、保存和导出。
- UI 仅通过应用接口创建配置和控制运行；后台执行不阻塞界面。验收按原第 14 节产品工作流执行。


### 20.8 测试策略

- 数学单元测试：贷款公式、概率/危险率、舍入、报表映射和借贷平衡。
- 状态机测试：任意合法起点、起止月份边界、月末关闭、结清后继续。
- 连续性测试：同一 trial 的完整运行与多个切分点 checkpoint 恢复逐项比较历史、账簿、状态和随机生成结果；从快照新建 trial 则不要求轨迹相同。
- 组合测试：Slice 顺序稳定性、冲突行为、同月因果、统一提交和幂等。
- 属性/不变量测试：借贷平衡、现金对账、贷款非负、期间连续、ID 唯一、来源引用有效。
- 固定 seed golden fixture 用于模型版本回归；统计性质测试使用固定 seed 集合与有容差的显著性界限，避免脆弱的单次随机断言。
- 测试覆盖不同持续时间，但不存在“模拟必须运行 240 个月”的业务断言。


### 20.9 已确定基线与后续技术决策

以下原则已由项目方向确定，不再作为启动编码的开放问题：

1. 月利率首版按名义年利率除以 12，按月初余额计息，月末先付利息再还本金；利息按币种最小单位四舍五入。付款低于利息时，差额按模型规则资本化并增加贷款余额；不模拟漏付、逾期或违约。
2. 首版复式账簿以个人/家庭持有一套房产为模拟主体，期初只需覆盖用户纳入该模拟范围的资产、负债和期初净值，不要求家庭完整资产负债表；v1 支持多项独立贷款，M2 先实现一笔固定贷款，M4 验收多笔贷款组合。具体科目编码、现金流分类和开账校验细节在 Ledger 实现阶段通过样例与测试确定。负物业净现金流是模拟结果，不代表家庭偿付能力，也不暂停模拟。
3. 随机模型按自然环境、房屋/组件、政策/宏观、居住/运营四类组织；首版范畴间独立处理。仅在具体模型证明有必要时再设计相关性。
4. 每月末产生完整模拟快照；用户可从任意快照创建新分支并重新抽样。父分支保留；新分支规则与参数可审计，抽样结果不要求和原分支一致。
5. 首版不保证应用升级后的数据向后兼容。相同分支的 checkpoint 恢复需避免重复提交；checkpoint 的精确持久化格式、故障重试细节在运行存储阶段定。

后续 ADR 用来固定实现细节、公式、科目样例及测试向量，而不重新打开已经确定的产品边界。遇到真实模型需求时版本化演进，不为假想需求提前构建通用规则语言或相关性插件框架。
