# ADR-22: M3 run inputs, snapshot references, and cash-flow aggregation

- **Status:** Accepted
- **Date:** 2026-10-20
- **Related:** [roadmap](../implementation-roadmap.md), [domain model](../domain-model.md), [ADR-13](ADR-13-ledger-profile.md), [ADR-14](ADR-14-mortgage-interest.md), [ADR-16](ADR-16-configuration-and-run-control.md), [ADR-20](ADR-20-composable-slices-and-random-sampling.md), [ADR-21](ADR-21-m3-run-randomness-and-persistence.md)
- **Test vectors:** M3 covers command validation and stop behavior, parent snapshot preservation, per-instance cash-flow attribution, and aggregation invariant under permutation and regrouping.

## Context

M3 needs a concrete backend boundary for run commands, completed snapshots and branch history, plus a result contract for contributions from composable Slice instances. It also needs a clear relationship between those contributions and the double-entry Ledger.

## Decision

- Run control is a backend API. Each invocation receives explicit user command parameters, including applicable configuration updates and whether to continue or stop. It validates updates, records their effective period, and decides whether to invoke the next monthly transition. A UI or CLI is not part of M3.
- Completed monthly snapshots and results are addressable records. Branch history is represented by branch identity and parent snapshot references; a dedicated tree container and loading every branch together are not required. A tree view can be derived from these references.
- Snapshot, run, branch, and trial identifiers are supplied by the caller and checked for uniqueness by the in-memory archive. A completed snapshot consists of its monthly result (including closing sufficient state, frozen input, active activity instances, trial and branch identity) plus the ending Ledger. The snapshot fields are encapsulated so callers cannot replace its Ledger after run control validates the result. Branch records contain their start month; the archive checks it against the first saved result, and child branches must start in the month immediately after their parent snapshot. Archive insertion checks branch/run/trial identity, parent references, and month continuity. Branching uses the selected snapshot's closing state, Ledger, frozen assumptions, and activity configuration, then starts at the following month under caller-supplied run/branch/trial identities and run boundaries. The required monthly executor interface receives the optional expected identity so it can produce matching output IDs. Latest editable user settings are stored independently and never replace the selected snapshot's configuration.
- Monthly results retain each active Slice instance's cash-flow contribution and provenance. Contributions describe the cash impact of committed economic activity and reconcile to the direct cash-flow projection from posted Ledger entries; they are not a competing cash balance or a substitute for postings. Period and cumulative totals are derived sums. Addition has an identity, is associative, and is commutative; reordering or regrouping contributions cannot change totals.
- A contribution is recorded per posted transaction and cash-flow category. Cash debits are positive and cash credits negative. Cash postings of the same category within one transaction are netted exactly; different categories remain separate, and a categorized transaction with net zero retains its contribution. Transactions without cash postings produce none. Contributions retain trial, branch, month, activity instance, Slice, model version, output key, and transaction ID.
- A balanced `StateAdjustment` supplied at the month-start input boundary is retained as a run-input posting with its update source and transaction ID. Its cash postings have a separate input-contribution record, because assigning it a fabricated Slice/activity identity would misstate provenance. Run-level/month-level cash-flow summaries include these input contributions alongside Slice contributions; per-activity summaries include only Slice contributions.
- Every accepted month-start `RunUpdate` is retained in the completed `MonthlyResult`, including its source and effective month. An economic `StateAdjustment` additionally produces a `RunInputEffect` recording prior and updated state and linking its Effect ID to the supplied transaction ID. This record is distinct from Slice Effects and is copied into snapshots through the result.
- In-memory archive summaries aggregate only months saved under the requested run ID. A child run therefore starts its cumulative view at its own first saved month; parent history remains queryable under its own run. Checked `Money` arithmetic reports representational overflow explicitly.
- Before sampling, the run boundary sums the rounded maximum absolute cash-flow support of every active Rental and Repair instance, the calculated interest/principal support of each active or updated loan, and each accepted state-adjustment transaction's net cash contribution by category. It rejects an unrepresentable support sum within any category; this bounds every monthly partial sum independent of contribution order or grouping. Loan coordination also checks the resulting totals for direct callers that do not pass through `SimulationRun`. A future Slice must contribute its own support bound to this validation.
- Monthly result construction also checks each instance's actual absolute contribution sum against its declared Rental/Repair support. This prevents a custom executor or Slice from returning cash postings outside the bound used to guarantee safe aggregation.
- The same associative and commutative composition contract applies to all accepted Slice instance results, not only cash-flow totals. Shared state effects combine only under a compatible reducer; incompatible writes are rejected before commit. Slice instances never consume one another's outputs.
- A fixed-rate, fully amortizing loan is an ordinary Slice instance whose opening balance is an in-scope liability fact. M3 uses ADR-14 for mortgages and other installment loans with those same terms: required calculation inputs are opening balance, remaining term, and fixed annual rate; the model derives the scheduled payment, interest expense, actual cash payment, principal reduction, and closing liability balance. The effective month is the first interest and payment month: it takes effect on day one, accrues a full month's interest, and makes the first payment at month-end. The monthly Slice effects and balanced Ledger transaction(s) update liability and cash; principal is financing cash flow and interest paid is operating cash flow. The continuation balance must reconcile to the Ledger liability. ADR-23 selects one liability account per loan and a shared interest expense account. Revolving, interest-only, variable-rate, and balloon structures are outside the M3 calculation scope and require their own convention before monthly behavior is modeled.
- When ordinary Slice outputs and loans share a month, prepare all postings against the same opening Ledger and preflight/commit them in one batch. Check each loan continuation against its independent liability account after that batch succeeds; do not reject a month because one Slice's provisional cash balance is outside the representable range when the complete month-end balance is valid.
- M3 does not model depreciation or amortization of property or other assets. These are non-cash valuation/expense rules and are outside the initial cash-flow scope; property carrying value remains the explicit opening/reference value unless a separately versioned valuation rule changes it.
- The first stochastic model is an implementation choice and does not require a pre-M3 model-selection decision.

## Alternatives considered

- Require a dedicated in-memory branch tree: rejected because parent snapshot references are sufficient and can produce a tree view without fixing storage to that representation.
- Require a separate Ledger account for every loan instance: left open here; resolved by ADR-23 in favor of separate accounts for M3.
- Permit ordered state transformations between Slice instances: rejected because ordering would make the monthly result depend on evaluation sequence.
- Generate record identifiers inside the archive: rejected because callers own stable retry identities and can choose IDs consistently across retries.
- Apply latest settings automatically when branching: rejected because the selected completed snapshot defines the continuation point; later settings must be explicit updates.

## Consequences

M3 can implement and test a small backend run API and record-based snapshot history without committing to a persistence engine or UI workflow. Results remain attributable to Slice instances while aggregate cash flow is independent of execution order and ties to Ledger cash postings. Loan continuation state and per-instance liability balances reconcile under the account granularity selected in ADR-23. Depreciation and amortization remain outside the initial model.
